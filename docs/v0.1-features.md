# FQL v0.1 feature list

Status: implemented v0.1 development release, verified locally. Checked items identify implemented capabilities and local acceptance evidence. Hosted CI, production deployment, and Android/iOS device acceptance remain separate verification boundaries; see [verification notes](verification.md).

## Release objective

A Flutter developer can define separate FQL model files, generate a typed Firestore client and reviewable Firebase configuration, and safely create, update, read, query, and observe documents through that client. Supported constraints are checked on writes and decoded reads, with database-side enforcement clearly specified.

Go powers the developer-time compiler. Dart/Flutter is the first runtime target. No application server is required.

## 1. Schema language and project organization

- [x] Separate model files in `fQL/schemas/`, such as `users.fQL` and `messages.fQL`.
- [x] Recursive discovery, deterministic ordering, and one combined project schema.
- [x] Project configuration outside model files, with schema location, generator target, and output paths.
- [x] Model names, explicit top-level collection paths, and document identity separate from stored fields.
- [x] Scalar fields: strings, booleans, integers, floating-point numbers, calendar dates, and timestamps.
- [x] Required, optional, and nullable fields with distinct semantics.
- [x] Basic constraints: string length, numeric bounds, and allowed scalar values.
- [x] Type-checked literal defaults on creation; no default substitution during reads or partial updates.
- [x] Explicit immutable fields, enforced on updates.
- [x] Explicit composite index declarations.
- [x] A minimal versioned language specification with valid and invalid examples.

Before implementing each type, specify its stored representation, Dart type, accepted range, and enforcement coverage. Calendar dates must distinguish valid calendar values from arbitrary strings; timestamps must define timezone and precision behavior. Reject unsupported enforcement requirements rather than silently approximating them.

## 2. Go compiler

- [x] Lexer and parser preserving file, line, column, and source spans.
- [x] Typed internal schema graph independent of Dart and Firestore code generation.
- [x] Duplicate model, field, and collection-mapping diagnostics.
- [x] Type, constraint, default, policy, index, and configuration validation.
- [x] Explicit errors for unsupported syntax, semantics, and versions.
- [x] Bounded input handling and malformed-input tests; no parser panics.
- [x] Stable, actionable diagnostics with correction guidance.

## 3. Generated Dart client

- [x] Typed models, document IDs, and Firestore serialization/decoding.
- [x] Ent-inspired create/update builders and field predicates, using idiomatic Dart APIs.
- [x] Create, fetch by ID, partial update, and delete operations.
- [x] Separate create and update inputs; distinguish unchanged, set, set-null, and remove operations.
- [x] Single-collection queries with supported equality/range predicates, ordering, limits, and cursor pagination.
- [x] Document and query subscriptions with resource cleanup and cancellation.
- [x] An injected official Flutter Firestore SDK instance, including emulator configuration.
- [x] Structured validation, decoding, not-found, permission, query, and SDK errors.

Exact generated API syntax is designed using short application examples before it is stabilized. Query combinations must respect the declared SDK support; unsupported combinations must not masquerade as working database operations.

## 4. Runtime protection and synchronization

- [x] Validate create and update inputs before submitting writes.
- [x] Validate decoded documents on direct reads, query results, cache reads, and listener events.
- [x] Fail explicitly on missing required fields, invalid types, unsupported values, and unknown stored fields. Do not silently omit invalid documents or coerce values.
- [x] Document failure behavior for an invalid document in a query result or live subscription.
- [x] Preserve official SDK caching and offline behavior for supported operations.
- [x] Distinguish local pending writes from server-confirmed state and surface later rejection.
- [x] Document schema-change behavior: regeneration does not modify existing documents, and incompatible existing data produces explicit errors.

## 5. Security Rules and indexes

- [x] Generate reviewable document validation rules for creates and resulting update state.
- [x] Include field allowlists, required fields, type/null checks, supported constraints, and immutable-field protection.
- [x] Minimal explicit authorization policies: deny, authenticated access, and ownership using an authenticated UID matched to document identity or a protected owner field.
- [x] Separate authorization for read, create, update, and delete; deny access without an explicit grant.
- [x] An enforcement matrix mapping each feature to client validation, rules enforcement, and any limitations.
- [x] Fail generation when a requested database guarantee cannot be represented accurately.
- [x] Generate Firestore index configuration from explicit schema declarations.
- [x] Document how authorization conditions affect allowed queries and which query predicates the caller must provide.
- [x] Document that privileged backend writers bypass Security Rules and require separate validation and authorization.

FQL generates artifacts; Firebase deployment remains an explicit developer action. Index generation does not infer every index an arbitrary runtime query might need.

## 6. CLI and developer workflow

These commands are implemented; see CLI help and the language specification for their contracts.

- [x] `fql init --target dart`: scaffold project configuration and separate schema files without overwriting existing work.
- [x] `fql validate`: validate the complete schema without writing generated artifacts.
- [x] `fql generate`: generate Dart code, rules, and indexes deterministically.
- [x] `fql generate --watch`: regenerate after schema/configuration changes and recover after errors.
- [x] `fql generate --check`: fail when generated artifacts are missing or stale; never modify files.
- [x] Schema/compiler compatibility metadata, without secrets or machine-specific paths.
- [x] Safe output ownership and cleanup, preserving handwritten files and previous artifacts on failure.
- [x] Useful help, nonzero failure codes, and documented installation.
- [x] Precompiled CLI archives with checksums for macOS/Linux on arm64 and amd64, plus Windows on amd64. End users do not need Go installed.

## 7. Verification and release evidence

- [x] Parser, semantic, diagnostic, and malformed-input tests in dedicated `tests/` directories.
- [x] Deterministic generation, safe-output, and stale-artifact tests.
- [x] Generated Dart formatting, analysis, compilation, and codec tests.
- [x] A runnable Flutter example with separate user and message schemas, CRUD, queries, and subscriptions.
- [x] Emulator tests for accepted and rejected writes, authorization, partial updates, immutability, queries, and indexes.
- [x] Malformed/older stored-document fixtures verifying read and listener errors.
- [x] Flutter integration evidence for local pending writes, reconnect behavior, and eventual server rejection; record the tested platform and SDK versions.
- [x] CI gates for the implemented compiler, generator, runtime, and emulator tests.
- [x] Installation smoke checks, a quick-start guide, supported-platform documentation, and known limitations.

The release is complete only when these capabilities work together in the example project. Generated text, unit tests, or emulator tests alone do not prove the entire workflow.

## Outside v0.1

- TypeScript/React Native generation and trusted backend runtime packages.
- Relationships, joins, referential integrity, cascade deletes, and uniqueness enforcement.
- Schema migrations, automated backfills, and automatic repair of old data.
- Arbitrary/unbounded maps and lists, subcollections, and collection-group queries.
- General-purpose SQL, raw query languages, custom validators, and plugin systems.
- Increment and array mutation transforms.
- Arbitrary authorization expressions, external role lookups, and automatic Firebase deployment.
- Multiple alternative client API styles, editor language servers, and visual schema tooling.

Managed server timestamps are now supported with explicit pending values; see [extensions](extensions.md). Increment/array transforms remain deferred.

## Implementation sequence

1. Language semantics, parser, diagnostics, and schema validation.
2. Dart models and strict codecs with generated-code checks.
3. CRUD, minimal authorization, generated rules, and emulator tests.
4. Queries, indexes, subscriptions, and synchronization behavior.
5. Initialization/watch/check workflows, binary distribution, and release documentation.

## Implemented extensions

- [x] First-class enums stored as member-name strings.
- [x] Named embedded objects and fully enforced bounded typed lists.
- [x] Managed created/updated server timestamps with pending/confirmed states.
- [x] Typed atomic batches and retry-aware transactions.
- [x] Schema diffs and explicit, bounded, read-only data auditing.
- [x] `fql format` validates the whole project before formatting; `--check` writes nothing.

See [extension contracts](extensions.md) for syntax, limits, operation costs, and compatibility rules.
